## Project overview

RestoreProof proves that Microsoft 365 backups in Veeam Backup for Microsoft 365 actually restore.

- **Worker** (`worker/`, C++20, Windows service): samples items from a Veeam restore point, restores them through Veeam's REST API v8 into three dedicated restore targets, reads them back through Microsoft Graph, compares, cleans up, signs and RFC 3161-timestamps the result, queues it in a local outbox and uploads it to the Cloud.
- **Cloud** (`cloud/`, FastAPI, Python 3.12): dispatches jobs, verifies and stores bundles, dashboard, monthly PDF reports for MSPs. Built so far (C5.1–C5.11): the app factory, settings, JSON logging, `/healthz`, the data model and its one migration, the local Compose stack, the repository layer (`app/repo/`, the only place a statement is built or run), the tokens and `current_worker` (`app/auth/`), the Worker's four routes `POST /v1/workers/register`, `GET /v1/jobs`, `POST /v1/results` and `POST /v1/heartbeat`, the job dispatcher (`app/scheduler.py`, the Compose `scheduler` service), the onboarding CLI (`cloud/manage.py` over `app/onboarding.py`, `docs/onboarding.md`), the contract (C5.11: `X-RestoreProof-API: 1` on every response, `GET /v1/version`, the 64 KiB body cap, the security scheme in the document, the CI diff, `app/contract.py`), and the login, the four dashboard pages and the audit page (C6.1–C6.3: `app/auth/{passwords,sessions,login_limiter}.py`, `app/audit.py`, `app/ui.py`, `app/routers/ui/`, Jinja2 templates, one stylesheet and vendored htmx 2.0.11, at the root and outside the OpenAPI document), and the report generator (C6.4: `app/report/`, a WeasyPrint A4 PDF per client and UTC month in two passes with two hashes, made by `manage.py generate-report` until C6.6's job and page); the admin routes (JSON) are not built. `cloud/tests` also runs the shared vectors, the schemas and `shared/tools/verify_bundle.py`.
- **Lab** (`lab/`, Python 3.12): the test tenant's canary seeder and Entra scripts. IDs in `lab/tenant.md`, the 40 canary items in `lab/seed-manifest.json`.
- **Shared** (`shared/`): the schemas, the test vectors and `verify_bundle.py`, the contract between C++ and Python.

Plan: `RestoreProof Stage 1 — Sprint Task Guide.docx`, 16 weeks, task IDs `L` lab, `W` Worker, `C` Cloud, `Q` quality, `S` sales, `P` pilots. ### The pipeline (`rpworker test`, as built through W4.11)

restore point → client check (the organisation `Office365`, `Worldwide`, `msid` = the profile's tenant; the manifest's tenant; the three targets resolved in that tenant) → clean before → sample (canaries + random) → target guard → restore (Veeam) → read back (Graph) → check → status → result built and validated (`restoreproof.result.v1`, invalid = `error result_invalid`) → clean after → timings → `--json <file>` (canonical bytes, never signed) **or** `--evidence <dir>` (`items.csv`, `veeam-session.log`, Ed25519 `signature.json`, RFC 3161 `timestamp.tst`, `result.json` last) → `--outbox <root>` renames the folder to `outbox\<run_id>` + `manifest.json` → `rpworker outbox flush` POSTs it to `<cloud_url>/v1/results`, 202 moves it to `sent\`.

The service (`rpworker service run`) runs that pipeline in process, one job at a time from `jobs_file`, writes `state\running.json` ahead of every step that matters, closes a run the process died in afterwards as `error interrupted|result_invalid|internal|job_invalid` (signed and queued like any run), holds while a restore of it may still run, flushes the outbox and POSTs a heartbeat to `/v1/heartbeat`.

## Non-negotiable rules

- **Restore targets.** Every restore goes to the `restoretest` mailbox, the `RestoreTarget` library in the RestoreTest site or alice's OneDrive `/RestoreTarget` folder (IDs in `lab/tenant.md`). Never the `RestoreTest` library or alice's `/RestoreTest` folder: those hold the canaries. `TargetGuard` runs per item inside `restore_sample` before any Veeam call, and again on the exact POST body; never trust configured IDs alone. The Cleaner is the only Worker code that deletes in the tenant: only in those three targets, each resolved through the guard's own checks first, only mails and plain files it has just listed there (`GraphClient::remove` takes a `ListedItem` only the Cleaner can make; a source scan enforces it); folders and anything else are never deleted. The app's write grants stay that narrow: `write` on the RestoreTarget list and the `/RestoreTarget` folder, `Application Mail.ReadWrite` scoped to `restoretest`; never `Sites.Selected` `write`, a `*.All` role or an Entra `Mail.ReadWrite` (`docs/security/graph-permissions.md`). Every run holds its client to the backup before anything is cleaned or restored (the client check; `error client_mismatch`); a job naming a connector this Worker lacks is `error connector_unknown` and never runs. The service's recovery adds no second deleter: its clean is the Cleaner's `before_run` clean by the record's own profile, never while a restore of ours may still run; in Veeam the hold ends only the sessions `running.json` lists as the run's own, and none of them while a restore request may have gone out and any other session of the account is running.
- **Status vocabulary.** `pass` = restore ran and 100% of items match; `fail` = an item missing or mismatched, its target read fine, Veeam not blaming infrastructure; `error` = the test itself couldn't run. Infrastructure problems are never `fail`. Veeam's own status never decides. The table is `docs/verification.md` and `rp/run_status.hpp`.
- **Secrets.** Only in the DPAPI vault (`vault.bin`; five names `veeam_username`, `veeam_password`, `graph_cert_pfx_base64`, `graph_cert_password`, `signing_key_base64`; filled by `rpworker vault set <name>` from the console or stdin, never an argument) or a gitignored `.env`. Never from an environment variable or `config.json` (which rejects secret-looking keys). Tests inject `Secrets` through each command's `load_secrets(vault)` seam. Never logged: `rp::redact()` masks the secret keys, JWTs, `Bearer` tokens and PEM private key blocks; headers and bodies are never logged. `veeam_username` is a name, not a secret value. The secret audit (`[secret_audit]`, and `fixture_secret_scan.py` with its allowlist) enforces this; `docs/testing.md` "The secret audit".
- **TLS.** Verification is never turned off. Veeam's self-signed certificate is trusted through `veeam_ca_file`, pinned through `veeam_cert_sha256` with only the host-name check skipped; a source scan fails the build on code that disables verification (reviewed exceptions all in `src/http_client.cpp`). `tsa_url` is the one URL that may be `http://`; a token is trusted for its signature, chain to `shared/tsa/tsa-ca.pem`, nonce and imprint, never for how it arrived. `cloud_ca_file` trusts a private CA for `cloud_url` (still https, host name checked).
- **Cloud tenant isolation.** All DB access through repo classes in `cloud/app/repo/` taking `msp_id: UUID` first and putting it in every `where` (`update` and `delete` too; a `get` of another MSP's row is `None`, a write of it is 0 rows); the only methods without it are `Lookup.find_worker_by_token_hash`, `Lookup.find_install_token_by_hash` (the two reads before an MSP is known) and `MspRepo.create`, held by an AST walk; `select(`, `update(`, `delete(`, `insert(` and `session.execute|get|add|scalars|…` outside `app/repo/` and `app/migrations/` (a migration runs on every MSP's rows by design) fail the lint test `tests/test_tenant_scope.py`, both walks reach a sub-package of `app/repo/`, and `tests/test_repo_isolation.py` holds every repo method on two MSPs (a new method must be added to its table; a sweep such as `RunRepo.requeue_stale` is marked `sweep=True` there, since with A's `msp_id` it may touch A's own rows and must leave B's). A connector's `config_json` is a `client-profile.v1` whose `graph_tenant_id` is its client's tenant (parsed, then compared as a uuid), and its client and Worker are read with `msp_id` by the repo itself, in the order schema, client, tenant, Worker, each refused as a `RepoError` naming the key and never a value (never left to the foreign key); every connector create, update or delete that touched a row writes one `audit_log` row in the same transaction, and one that touched none writes none; a connector's Worker and client never change. The repos flush and never commit. The database holds the same line by key (C5.2): every table but `msp` has `msp_id NOT NULL` with a key to `msp`, and every other foreign key is composite and starts with `msp_id`, so no row can point at another MSP's row; a tenant is one client per MSP (`client.tenant_id`, a `uuid`), a connector is one per Worker and client, a plan is on its own client's connector and a run under its plan's client; no foreign key cascades. A new table follows these rules, and a new migration is written by hand, names every constraint and imports nothing from `app.models`.
- **Worker tokens.** A token is 32 random bytes in base64url (43 characters); the database holds its SHA-256 alone (`worker.api_token_hash`, `install_token.token_hash`), the token is shown once and stored nowhere. `current_worker` takes it from `Authorization: Bearer <token>` (one space, nothing else), hashes, looks up, compares with `hmac.compare_digest`, and answers one 401 `{"detail": "not authenticated"}` with `WWW-Authenticate: Bearer` after the same work for a missing header, an unknown token and a revoked Worker (`revoked_at` set to anything); nothing tells a caller which. The empty token (no header, or a header of another shape) is refused after that work whatever the database holds, so a Worker row under `sha256("")` authenticates nothing. An install token expires at exactly seven days and is used once, by one `UPDATE` whose conditions are in the statement; it carries a `label`, `created_at` and `created_by` and names no client. **Registration** (C5.5, `POST /v1/workers/register`, `app/auth/registration.py`): the install token first (one 401 after the same work for an unknown, used or expired token, whatever its shape), then the key (400 for a file outside the verifiers' key-file rule, a non-canonical encoding, a `y` that is no point of the curve, or one of the fourteen small-order encodings, `app/auth/public_keys.py`; the eight points are refused because the library verifies forgeries under them, an off-curve value because nothing could ever verify under it and the operator should hear at enrolment), then `uq_worker_key_id` (409), so nothing but a 401 is answered without a valid install token; the API token is minted with `new_token()`, hashed into the row, answered once with `worker_id` and `key_id`, and the whole of it (the token's `UPDATE`, the Worker, one `audit_log` row `worker.register`) is the request's one transaction, committed before the 201 starts (`SessionDep`), so a 400 or a 409 leaves the install token unused and the Worker's first poll finds its row. The stored `public_key_pem` is the library's one three-line serialisation and `key_id` the SHA-256 of the DER, unique across all MSPs. `WorkerRepo.create` refuses `sha256("")` as a `RepoError`. Neither a token nor its hash reaches a log line (a test holds it).
- **Dispatch** (C5.6, `GET /v1/jobs`): the Worker's oldest queued runs, at most five, moved to `dispatched` with `dispatched_at` and `attempt + 1` in one statement (`RunRepo.dispatch`: a `MATERIALIZED` CTE under `FOR UPDATE SKIP LOCKED`, never `id IN (subquery)`, which Postgres rescans per outer row so the limit slides), answered as a `restoreproof.jobs.v1` document whose `run_id` is `str(test_run.id)`, `client_id` `str(client.id)`, `client` the connector's `config_json`, `connector` its type, the sizes the plan's, `restore_point` `latest`, `screenshots_enabled` the client's, no `canary_cursor`; validated against `shared/schemas/jobs.v1.json` in a test, not per request; a busy poll is three statements and an idle one two, held by a test. Every refusal a route makes is in `docs/api/openapi-v1.json` (`ErrorBody`). There is no `received` state (C5.7): the bundle's status is known in the request that receives it; `RunRepo.requeue_stale` (the sweep C5.9 calls per MSP) puts a run dispatched six hours ago or more back to `queued`, or to `expired` at three attempts, and its bundle is still taken when it comes.
- **Bundle upload** (C5.7, `POST /v1/results`, `app/results.py` and `app/routers/results.py`; `docs/verification.md` "The Cloud receives a bundle"): the Worker's parts as `outbox.cpp` sends them (`result`, `signature`, `timestamp` when there, one per listed attachment under its name), identified by name alone; the route reads the form itself under explicit limits (415 not multipart, the media type in any case; 411 no `Content-Length`; 413 over 96 MiB before the body is read, and again on the bytes as they arrive, since h11 frames a chunked body beside a small `Content-Length` by its chunks (`_Body`, held through uvicorn by `tests/test_results_server.py`); `body: malformed`, also for a sender that went away; `part_twice`; a part over its verifier limit is refused unread), since nothing else in the stack bounds a body; it calls starlette's `MultiPartParser` directly, never `request.form()`, and closes the form. `verify_upload` runs in a thread (`asyncio.to_thread`), never on the loop. The Cloud **is** the Python verifier: `shared/tools/verify_bundle.py` imported by path from the image (never copied), its `verify`, `check_attachment` (public since C5.7) and `check_timestamp` in the verifiers' order under the token's Worker's `public_key_pem` and `key_id` (never anything in the body) and the one root `shared/tsa/tsa-ca.pem`; every refusal is 400 with the verifier's bare word, a part the result doesn't list is `part_unexpected`, a listed size over 25 MiB 413, a missing token `tsa_ok` null and a bad one refused (the three verifiers agree on every shared vector; two upload cases differ by design and are named in `tests/test_results_vectors.py`). A verified result the tables can't hold (an item `index` over int4, a U+0000 in a text a row takes) is 400 `result_unstorable`, the Cloud's own word, never a 500. The run is named only after the whole verification, by the exact text `str(test_run.id)`: one 404 `run_id: no such run` (no uuid or one in another spelling, unknown, another MSP's, another Worker's), 409 `run_id: not dispatched` for `dispatched_at` null, `dispatched`, requeued `queued` and `expired` runs all taken (a late `error interrupted` lands), 409 `client_mismatch` (`client.client_id` = `str(client.id)`, `tenant_id` and, with `scope` `same_tenant`, `resolved.organization.tenant_id` parsed as uuids = `client.tenant_id`, no `pass`/`fail` without `same_tenant`; an `error` without the check may carry `tenant_id` `""`, the Worker's `job_invalid` for a profile it couldn't read), 409 `bundle_conflict` for a second bundle of one run, 202 with the stored state and nothing written for the same bundle again. Rows first then objects in the request's one transaction: `RunRepo.receive` (one `UPDATE`, which also stamps `received_at` with the route's `now()`, the Cloud's clock a report's month goes by for a late result; the rowcount settles a race with another upload; on 0 the row is read again and decides, nothing is tried twice; `FINISHED_STATES` is `RUN_STATES` without `RECEIVABLE_STATES`, held by a test), `ItemRepo.create_many` (one row per `expected.items[]` joined to `check.items[]` by `index`, `position` the index, `found_sha256` always null), one `audit_log` row `result.received` `run:<id>`, then `Storage.put` under `msp/<msp_id>/runs/<run_id>/<file name>` (`bundle_key` is that prefix); 202 `{"run_id", "state"}` committed before it leaves, never a 200. A refusal after authentication writes one audit row `result.rejected` with `worker:<id> <word>` (or `run:<id> <word>` once the run is known) and is returned, not raised, so that row commits and nothing else; no refusal's text and no log line quotes the body. `app/results.py` is under `tools/check_coverage.py` at 100% line and branch.
- **Heartbeat** (C5.8, `POST /v1/heartbeat`, `app/routers/heartbeat.py`; `docs/verification.md` "The Cloud receives a heartbeat"): the body is the Worker's five keys as `worker/src/heartbeat.cpp` sends them (`version`, `last_error`, `last_error_at`, `outbox_depth`, `uptime_s`), closed, every key required, each held to the Worker's own form (`version` as registration's; `last_error` the shape `^[a-z0-9_]{1,64}$` or null, never the Worker's list; `last_error_at` exactly `YYYY-MM-DDTHH:MM:SS.mmmZ` on a real day or null, both or neither; the counts strict integers 0 to 2^53 − 1), anything else FastAPI's 422; the issue's four keys were never what the Worker sends. **The token before the body:** the body is never a parameter of the route (FastAPI reads and parses a body parameter before any dependency); `heartbeat_body` depends on `current_worker` and reads the request itself, so no, another or a revoked token is the one 401 after `current_worker`'s one lookup with nothing of the body read, and for the Worker a body that isn't `application/json`, can't be parsed (not JSON, too deep, a number past the interpreter's digits) or names a key twice is the same 422, never FastAPI's 400; `last_error_at` is parsed once into the stored time, `version` is `routers/workers.py`'s `Version`, the type registration uses. One `UPDATE` (`WorkerRepo.heartbeat`, `revoked_at IS NULL` in the `WHERE`, 0 rows the same 401 and nothing written; the default session synchronisation, never `synchronize_session=False`, so the Worker the dependency loaded isn't left stale): `last_seen_at` is the Cloud's clock (`now()`), never a body time; the five fields are stored as sent, a null replacing a value (a restarted service clears its error). Two statements (that lookup and the `UPDATE`), no row read back, no audit row, nothing of the body or the token in a log line. 204 with no body and no `Content-Type`; the Worker takes any 2xx and reads nothing. `last_seen_at` is written by the heartbeat alone (not the poll, not the upload).
- **Cloud settings and logs.** Nothing that is a secret or an address has a default in `app/settings.py`; the local stack's `local-only-...` values live in `docker-compose.yml` alone, and a settings fault names the variable, never a value. Times are aware UTC (`UtcDateTime` refuses a naive one).
- **Signing contract** (C++ and Python agree, held by `shared/testdata/`): `canonical-json-v1` (`rp::canonical_json`; keys sorted by byte, `,` and `:` only, no trailing newline, refuses floats, integers outside ±(2^53−1), non-ASCII keys, invalid UTF-8; Python's `json.dumps(sort_keys=True, separators=(",", ":"), ensure_ascii=False)` gives the same bytes). `result.json` is the result's canonical bytes with nothing removed; `bundle_sha256` is its SHA-256; the signature is Ed25519 over the 32 raw digest bytes, in `signature.json` beside the result (`restoreproof.signature.v1`, five keys), never in it; `timestamp.tst` is the bare RFC 3161 token over the same digest, absent when the TSA gave none (never a status). A verifier takes the public key and the TSA CA from its caller, never the folder, and refuses a `result.json` that isn't its own canonical form (`result_not_canonical`). `rpworker signer verify` and `shared/tools/verify_bundle.py` run the same checks in the same order and print the same word; the schemas in `shared/schemas/` are the only copies (the result schema embedded into rpcore at build time, read by the Cloud by path) in the subset draft 7 and 2020-12 read alike; whoever validates in Python checks the canonical form first. The run folder's other files are covered only through the result's `attachments`; `result.json`, `signature.json`, `timestamp.tst` and `manifest.json` are never listed there.
- **API contract** (C5.11; `docs/verification.md` "The contract"). All Cloud routes under `/v1` (`/healthz` is the one probe outside it and not in the OpenAPI document; a test holds both); every response the app sends carries `X-RestoreProof-API: 1` from the outermost middleware (not uvicorn's own 400 for a request it can't parse or its 503 under `--limit-concurrency`, which never call the app: only a 2xx is held to the header) (`app/contract.py`; the value is the contract's number, the `1` of `/v1`, never the Cloud's version, and it changes only with `/v2`); `GET /v1/version` answers `{"api": 1, "version": app.__version__}` with no token and no statement; every request body but `POST /v1/results`' is held to 64 KiB on the header and on the bytes, 413 `body: too large` (the upload keeps its own 96 MiB cap and is known by the path the router matches, `get_route_path`, never `scope["path"]`, which carries the server's `root_path`; a `Content-Length` of more digits than the cap's is over it and never converted; the token still comes before the body, since the header check reads nothing); the three routes that take the bearer token are documented as such by `current_worker`'s own `HTTPBearer(auto_error=False)` dependency, never read, so the document follows the code (registration's install token is in its body: no scheme); `docs/api/openapi-v1.json` is committed since C5.6, held equal to what the app serves by `tests/test_openapi.py` (regenerate it with `tools/dump_openapi.py`) and by `cloud.yml`'s `contract` job (regenerate and `git diff --exit-code`; a PR's change of the file goes into the step summary, never fails). The contract test is the Worker-written `shared/testdata/signing-v1/dispatched-run.json` posted unchanged to 202, to the run a poll of `GET /v1/jobs` dispatched with the vector's `job` as its answer, key for key; nothing in a Cloud test re-signs it. "No test, no merge" also holds `cloud/manage.py` and `shared/tools/` to a test under `cloud/tests/`.
- **Login and pages** (C6.1–C6.3; `docs/verification.md` "The Cloud's pages"). The pages live at the root, outside `/v1` and never in the OpenAPI document (`ROOT_ROUTERS`, `include_in_schema=False`; a test holds the document to the five API routes), and still carry `X-RestoreProof-API: 1` and sit under the 64 KiB cap. Every statement is a repo method with `msp_id` first; a page of one MSP never shows another's row, and a row of another MSP is **404, never 403** (403 is a member on an admin route alone); a page runs a fixed number of statements whatever its rows. A password is Argon2id under argon2-cffi's defaults, 12 to 1024 characters, read by the CLI from the console twice or from stdin as one line, **never an option, an environment variable, a log line or a page**; a known and an unknown address cost the same work at login (the unknown hash); every `POST /login` counts towards five a minute per address and per IP, the sixth is 429 before any password work; an attempt on a known user is one `audit_log` row (`login.success`, `login.failure`, `login.blocked`), an unknown address has no MSP and no row and one `login refused` line with nothing of the form. The session is the one cookie `rp_session` signed with `SECRET_KEY` (its only use) for 12 hours; `current_user` reads the user's row every time and a cookie carries the stamp of the password it was issued for (`password_stamp(user.password_changed_at)` of the row the login read, whole microseconds), compared for equality and never as times, so a cookie of another `password_changed_at` is no session whatever the three clocks say; no session is 303 to `/login` for a browser and 401 with `HX-Redirect` for htmx; a page's `POST` from `cross-site` or `same-site` is 403, and so is the download, the one `GET` that writes. `POST /login` holds its two fields itself (never `Form(max_length=)`, whose 422 repeats the refused value): a missing, over-long or non-UTF-8 field is 422 with the login page and nothing of the form; an address `check_email` refuses is nobody's and is never looked up; the lookup lowers both sides in PostgreSQL. A refused attempt adds no key to the limiter's table. **Nothing of a login reaches a log line:** no address, no password, no cookie, no form body (a test scans). Every template autoescapes (`StrictUndefined`, a planted `<script>` escaped on every page); no page repeats a secret, and no page links the bucket: a download is `GET /runs/{id}/files/{name}`, which writes `bundle.download` with the user and the address and only then 302s to a URL pre-signed for ten minutes against `S3_PUBLIC_ENDPOINT`. `/workers`' Revoke is `onboarding.revoke_worker` with the user and the address, the CLI's function and its one row; `/audit` is the admin's, newest first, the last 30 days by default, and **nothing deletes an audit row** (C7.3 names the rule). `app/audit.py` is the pages' one writer (`record`, `client_ip`) and `ACTIONS` the closed list of their words; a word is added by the task that writes it. `app/auth/` stays under `tools/check_coverage.py` at 100% line and branch, the three new files included.
- **Report wording.** Never claim more than was tested; "fully recoverable", "guarantee", "certified", "accepted by insurers" are banned by a test (`tests/test_report.py`, against the template, the stylesheet, the controls, both rendered passes and the PDF's text).
- **Reports** (C6.4, `app/report/`; `docs/verification.md` "The Cloud's report"). A report is one client's PDF of one UTC calendar month (`YYYY-MM`), six sections in the issue's order. A `pass`, `fail` or `error` run is the month's by `coalesce(finished_at, tsa_time, dispatched_at, created_at)` (a result written afterwards has no `finished_at` and is never dated by its queueing), **unless the Cloud received its result at 02:00 UTC on the 1st after that month or later** (`test_run.received_at`, stamped by `RunRepo.receive` with the upload route's `now()`; `RESULTS_CLOSE` two hours): then it is the month's it was received in, since the month it ended in may have its final report, so every result is a test of exactly one month; the report prints such a run with its own date, orders the month by the tests' ends and counts it on the Summary line "Tests that ended before this period and whose results arrived after that period had closed, counted here: N"; **no final report is made before 03:00 UTC on the 1st** (`FINAL_AFTER` three hours, `generate`'s `period: not closed until 03:00 UTC on the 1st` for whoever asks, the hour between the two the room an upload has to commit; a test holds the constants' order); every other run by `created_at` and is not a test: `expired` is "did not run", `queued` and `dispatched` are "no result yet", each counted on its own line in the Summary (a month whose Worker was off must not read as a month of passes); `app/repo/runs.py`'s `period_time` and `period_filter` are the one rule, `data.py`'s `run_date` the run's date (`_run_time`) on a row, and the four reads of a month share it. The overall line keeps `fail` and `error` apart and never adds them, and is in the pass colour only when a test ran; the Summary says what the three words mean; recovery times and restore points are the `pass` and `fail` runs' alone. An item with `match` unknown is "not checked" whatever `found` says, never "missing". A failure's later pass is one of its own plan ("A later test of the same plan passed", never "re-tested"). The Method names only plans with a result in the period and claims a level only when a test passed or failed, level 4 only when one sampled a file. No text is laid out past the page (a layout test). The report is rendered **twice** from one `ReportData`: pass 1 without the hash, its SHA-256 the content hash printed by pass 2, whose SHA-256 is the file hash; both in `report.content_sha256` and `file_sha256`; the PDF says why in one sentence; the same HTML is the same bytes by one WeasyPrint version (its defaults embed no date or id; the file names `/Producer` `WeasyPrint <version>`, read through pypdf; `SOURCE_DATE_EPOCH` pinned for fontTools), held by a test; rendering runs in a thread. A month has one final report per client (`uq_report_final_period`, asked by `ReportRepo.final` before rendering: `period: already reported`, which is also the word for a final insert either unique refused, so the loser of two at once is `existing` to the job) and any number of interim ones (a period not over: `interim_for`, the title "Interim report", the key with the generation time); the object `msp/{msp_id}/reports/{client_id}/{YYYY-MM}.pdf` (interim: `…-interim-{YYYYMMDDTHHMMSSZ}.pdf`) is put **after** the row and the one audit row `report.create` `report:<id>`, so a refusal writes no object and a failed put rolls the row back; a render or a put that fails is a `ReportFailed` (`report: not rendered (<type>)`, `storage: put failed (<type>)`, the type alone), never left to the caller's guess; nothing edits, replaces or deletes a report. The PDF holds no token, key PEM (the `key_id` alone), pre-signed URL, bucket name, `http`, tenant id or person's address; the template renders under `ui.make_environment` (autoescape, `StrictUndefined`) and a planted `<script>` is escaped in both passes. `gather` is eight reads with `msp_id` first whatever the rows; `generate` nine, the row, the audit row, the put; another MSP's client is `client_id: no such client`. The Framework mapping section (C6.7) names the four controls by their own words (the SOC 2 row by the criteria's words, never a gloss) with one sentence each for what a test marked pass shows ("On the dates listed, a sample of items was restored …"; a report with no test marked pass prints `NO_PASS` there instead, "No test in this report is marked pass, so it shows nothing for this control.") and what the report does not look at, under a sentence that the table describes this evidence and is not an assessment of the control; **every reviewed sentence** of the Summary, the Method, the cap's line, the Integrity sentence and the mapping is held verbatim by `tests/test_report_wording.py` (C6.5): a wording change changes that list in the same commit, and the readers' comments are their own entries in `docs/decisions.md`. **The cap** (C6.6): the Test log, the Failures and the Integrity run list show the first `MAX_LOG_ROWS` (200) runs of the month in the month's order with a line saying how many more there were; the Summary counts every run. **The job** (C6.6, `app/scheduler.py` `tick_reports`): the 1st at 03:00 UTC and once at start, the newest closed month's final report (`closed_month`: the previous month from 03:00 on the 1st, the one before it until then, so a start at 00:00:30 makes nothing of the month that just ended) for every client with a run in it (`RunRepo.clients_in_period`, any state), one transaction per client committed as made, `period: already reported` counted as `existing` and never a failure, a client's failure logged by type (`report failed`) while the next is made, a report named (`report created`) after its commit; ## TDD workflow (enforced by CI)

- Test first: an acceptance test from the task's "Done when", then red → green → refactor per step; commit test and code together.
- Anything talking to Veeam, Graph, the TSA or the Cloud is written against recorded fixtures first (`--record`, secrets scrubbed, served by `FakeHttpClient`). Live calls are gated by `RP_LIVE=1` (`docs/testing.md`). Catch2 assertions aren't thread-safe: never in code a fake handler runs on the client's threads.
- Failure-path tests before happy paths; decision tables as Catch2 `GENERATE` / `pytest.mark.parametrize`; every bug gets a reproducing test before its fix; end-to-end scenarios tracked by hand in `tests/e2e/scenarios.md`.
- Cloud database tests run on a real PostgreSQL 16, never SQLite and never `metadata.create_all`: the schema is what `alembic upgrade head` built, each test runs in a transaction that is rolled back, a refusal is held to its constraint's name, and a database that can't be reached is a failure, not a skip.
- Exe tests check exit code, stdout and stderr exactly (no `PASS_REGULAR_EXPRESSION` or `WILL_FAIL`); none starts the service loop or names `service install|uninstall|start|stop`; no test touches `%ProgramData%`.
- Coverage: 80% line on `rpcore` and `cloud/app` (Cloud gate on line+branch combined); 100% on the strict files, held as 100% **line** in the Worker since OpenCppCoverage has no branch data. `tools/check_coverage.py` measures `app/repo` and `app/auth` since C5.3/C5.4, `app/results.py` since C5.7, `app/cadence.py` since C5.9, `app/contract.py` since C5.11 and `app/report` since C6.4 (every guarded path exists): every branch of a repo, auth, results or report file needs a test (`public_keys.py` and `registration.py` are under it since C5.5). A Worker file is strict when a part of its path is, or starts with, one of `vault`, `signer`, `target_guard`, `run_status`, `cleaner`, `timestamper`, `outbox`, `service`, `client_profile`, `strict_json`, `client_check` (`worker/tools/coverage_gate.py`); strict files are decided logic over seams, no `catch (...)` of their own, and the real calls under them (`ed25519.cpp`, `rfc3161.cpp`, `uploader.cpp`, `folder_ops.cpp`, `scm.cpp`, `stop_signal.cpp`, `worker_body.cpp`, `heartbeat.cpp`, `run_folder_tail.cpp`) are outside. Cloud: 100% on `app/auth`, `app/results.py`, `app/repo`, `app/cadence.py`, `app/contract.py`, `app/report`. Every `.cpp` under `worker/src`, `include` and `app` must appear in the report.
- "No test, no merge": a PR changing `worker/src|include|app` without C++ test changes under `worker/tests/`, or `cloud/app/`, `cloud/manage.py` or `shared/tools/` without a `.py` under `cloud/tests/`, fails CI (C5.11 added the last two).

## Coding conventions

- rpcore works in UTF-8 and reads Windows text through the wide APIs only. Messages are one line of fixed words and counts; never `what()`, a tenant value, a path or a secret in a status, a code or a log line that could leave the machine. Every logged string goes through `redact()`; `SECURITY:` lines mark a guard or owner-rule refusal.
- A new architectural choice gets a dated entry in `docs/decisions.md` (recorded before the build; "approved as written" when the owner approved it), its build notes say where the build left the entry, and the code review gets its own entry listing fixed and open findings. Update `docs/verification.md`, `docs/worker-config.md`, `docs/testing.md`, `docs/glossary.md` and this file with the task.
- Shared documents (`shared/testdata/result-v1`, `signing-v1` (`dispatched-run.json` by `[.write_shared_dispatched]`, the one that reaches 202), `timestamp-v1`, `canonical-json-v1.json`, `client-profile-v1`, `jobs-v1`) are written by hidden `rptests "[.write_shared_*]"` cases and run by both builds; a shared document names no person (the W4.1 rule: `result-v1/valid.json` is renamed after its run, and a signed folder's job samples nothing whose read-back names one; `person_named` in `worker_body_test.cpp` holds `dispatched-run.json` to it: the admin's name in any case and either half, and every address's local part and personal site's owner one of the test accounts `alice`, `bob`, `restoretest`); `dispatched-run.json` is the one shared document with the lab tenant's identifiers, and says so; `.gitattributes` keeps `shared/schemas/*.json` and `shared/testdata/**/*.json` LF. Keys in vectors are RFC 8032's published test keys, never a secret.
- Live evidence goes under `docs/api/veeam-lab/<task>-*` with its harness; run folders, profile files and config copies stay outside the repo (`%LOCALAPPDATA%\RestoreProof\lab\`). A live harness uninstalls the service whatever happens and never replaces committed evidence with a failed run's.
