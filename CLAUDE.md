## What the product does

RestoreProof proves that Microsoft 365 backups in Veeam Backup for Microsoft 365 actually restore. An on-prem **Worker** (C++, Windows service) samples items from a Veeam restore point, restores them through the Veeam REST API (v8) into dedicated test locations, reads them back through Microsoft Graph, compares them, cleans up, and uploads a signed, RFC 3161-timestamped result bundle. A **Cloud** backend (FastAPI) dispatches jobs, verifies and stores bundles, shows a dashboard, and generates monthly PDF reports for MSPs.

Worker pipeline (`rpworker test`, as built through W4.6): pick restore point → cleanup → sample select → target guard → restore → verify → status → result built and validated (`restoreproof.result.v1`; invalid: `error result_invalid`) → cleanup → timings → result JSON (`--json`: the finished result validated again, written as its canonical bytes, never signed) or the run folder (`--evidence <dir>`: `items.csv`, `veeam-session.log`, then the result signed, Ed25519 over the SHA-256 of its canonical bytes, then a TSA asked for an RFC 3161 token over the same hash, `signature.json`, `timestamp.tst` when there is a token and `result.json` last, listing the attachments with their hashes; with `--outbox <root>` the finished folder is then renamed to `<root>\outbox\<run_id>` and gets its `manifest.json`, and `rpworker outbox flush` posts each queued run to `<cloud_url>/v1/results` and moves it to `<root>\sent\<run_id>` on 202); still planned: upload (the Cloud's `/v1/results` and the API token, W5.1; until then the endpoint is a stub and no credential is sent).

## Non-negotiable rules

- **Restore targets:** every restore goes to the `restoretest` mailbox, the `RestoreTarget` library in the RestoreTest site, or alice's OneDrive `/RestoreTarget` folder (IDs in `lab/tenant.md`). Never to the `RestoreTest` library or alice's `/RestoreTest` folder: those hold the canary files (`docs/decisions.md`, 2026-09-25). `TargetGuard` must be checked per item, inside `RestoreSample`, before any Veeam call. Any code path that could target something else is a bug. The same holds for deletes: the Cleaner (W3.4) is the only Worker code that deletes in the tenant, only in these three targets, each resolved through the guard's own checks first, and only items it has just listed there (`GraphClient::remove` takes a `ListedItem` only the Cleaner can make; a source scan enforces it). The Worker app's write grants stay that narrow: `write` on the RestoreTarget list and on alice's `/RestoreTarget` folder, `Application Mail.ReadWrite` scoped to `restoretest`; never `Sites.Selected` `write`, a `*.All` role or an Entra `Mail.ReadWrite` (`docs/security/graph-permissions.md`). Folders and anything else that isn't a plain file or a mail are never deleted.
- **Status vocabulary:** `pass` = restore ran and 100% of items match; `fail` = an item missing or mismatched, its target read fine and Veeam not blaming infrastructure for it (a failed restore counts only through its missing items; W3.3); `error` = the test itself couldn't run (Veeam unreachable, Graph auth/permission error, guard violation). Infrastructure problems must never be reported as `fail`. The decision table lives in `docs/verification.md`.
- **Secrets:** only in the Worker DPAPI vault (`%ProgramData%\RestoreProof\vault.bin`, W4.5: `rp/vault.hpp`, machine-scope DPAPI, a protected ACL of SYSTEM, Administrators and the file's owner plus one Read entry per `rpworker vault grant <account>`; read once per command into `Secrets` under five names, `veeam_username`, `veeam_password`, `graph_cert_pfx_base64`, `graph_cert_password`, `signing_key_base64`, in `worker/include/rp/secrets.hpp`; filled by `rpworker vault set <name>` from the console without echo or from stdin, never from an argument) or gitignored `.env`. No secret is read from an environment variable anywhere in the Worker (the `RP_*` secret variables are gone; `RP_LIVE`, `RP_LIVE_VAULT` and the other switches are not secrets) nor from `config.json`, which rejects secret-looking keys; the unit tests inject `Secrets` through each command's `load_secrets(vault)` seam and the live tests read the vault through `tests/live_secrets.hpp`. Never logged; HTTP logging redacts `Authorization`, `client_secret`, `client_assertion`, `password`, `refresh_token`, `access_token`, `pfx`, `applicationCertificate`, `applicationCertificatePassword`, `signing_key`, `signing_key_base64` and `signing_private_key` keys, raw JWTs, `Bearer` tokens and a PEM private key block through `rp::redact()`, and never logs headers or bodies. A sentinel-grep test (W4.9) enforces this.
- **TLS:** verification is never turned off. A self-signed Veeam certificate is trusted through the `veeam_ca_file` config key, never by skipping verification. Veeam's default certificate names no host (no SAN): with `veeam_cert_sha256` also set, its public key is pinned, the chain is still verified against the CA file, and only the host-name check is skipped (`docs/decisions.md` 2026-09-26, "Veeam TLS"). A source-scan test fails the build if code that disables verification appears; its only reviewed exceptions are W1.3's best-effort revocation call, W1.5's pin statements and Q2.1's loopback-only socket callback (unit tests only), all in `src/http_client.cpp`. The TSA's URL (`tsa_url`, W4.4) is the one that may be `http://`: nothing is turned off there (an `https` TSA is verified like any other call), and a token is never trusted for how it arrived but for its signature, its chain to the pinned root, the nonce and the imprint, all checked before it is written.
- **Cloud tenant isolation:** all DB access goes through repo classes in `cloud/app/repo/` that take `msp_id` first. `select(` outside `app/repo/` fails a lint test.
- **Signing contract (shared by C++ and Python):** canonical JSON = sorted keys, no whitespace, UTF-8, ISO-8601 UTC; `bundle_sha256` is the SHA-256 of `result.json`'s bytes, which are the result's `canonical-json-v1` form, with nothing removed; the signature is Ed25519 over the digest's 32 raw bytes (not its hex text) and lives in `signature.json` beside the result (`restoreproof.signature.v1`, five keys, schema `shared/schemas/signature.v1.json`), never in the result; a verifier takes the public key from its caller, never from the folder, and refuses a `result.json` that isn't its own canonical form (amended by W4.3, `docs/decisions.md` 2026-10-05 W4.3 point 2; the guide's "with `signature` and `tsa_token` removed" can't be built, and the timestamp is a file of its own: since W4.4 `timestamp.tst`, the bare RFC 3161 token over that same digest, obtained after the signature, checked by both verifiers against a CA the caller gives, `--tsa-ca`, never one from the folder, and absent when the TSA gave none, which is "not timestamped" and never a status). The canonical form is `canonical-json-v1` (W4.1, `rp::canonical_json`): keys sorted by byte, `,` and `:` only, no trailing newline, strings as UTF-8 with JSON's short escapes and lower-case `\u00xx` for the other control characters; it refuses, never rewrites, a floating-point number, an integer outside ±(2^53 − 1), an object key that isn't ASCII and invalid UTF-8, so Python's `json.dumps(sort_keys=True, separators=(",", ":"), ensure_ascii=False)` gives the same bytes; vectors in `shared/testdata/canonical-json-v1.json`, run by both builds (since W4.3 the Python side is the canonicaliser in `shared/tools/verify_bundle.py`, with the same refusals). Schema is one file, `shared/schemas/result.v1.json`, used by both builds: embedded into the Worker at build time, read by the Cloud by path, and written in the subset of JSON Schema that draft 7 and 2020-12 read alike (`docs/decisions.md` 2026-10-04 W4.1 point 3); a float passes Python's `integer` as `1.0`, so whoever validates in Python (C5.7, `verify_bundle.py`) checks the canonical form before the schema. (`shared/schemas/` also holds `seed-manifest.v1.json`, the canary manifest's schema, and `shared/testdata/` the test vectors W3.2's C++ checker must pass: `text-v1` for mail bodies and `office-v1` for docx/xlsx content, which SharePoint rewrites; see `lab/README.md`.) `shared/tools/verify_bundle.py` is the auditor-facing verifier (W4.3) and must agree with the C++ `Signer`: the same checks in the same order with the same word on stdout as `rpworker signer verify`, which the shared vectors in `shared/testdata/signing-v1/` hold both builds to. The run folder's other files (W4.2) are covered only through the result's `attachments` (name, SHA-256, size), which are inside the signed bytes; `result.json` and `signature.json` are never listed there.
- **API contract:** all Cloud routes under `/v1`; `docs/api/openapi-v1.json` is committed and diffed in CI.
- **Report wording:** never claim more than was tested. Phrases like "fully recoverable", "guarantee", "certified", "accepted by insurers" are banned by a test.
- Failed runs are never edited or re-signed. Nothing in a queued or sent run folder is written after the run but the outbox's own `manifest.json` (W4.6), which is never uploaded; the Worker never deletes a queued run, only `sent\` runs the Cloud has answered 202 for (older than 30 days, or the oldest while `outbox\` and `sent\` hold over 500 MB).

## TDD workflow (enforced by CI)

- Test first: acceptance test from "Done when", then red → green → refactor per step; commit test and code together after each green.
- Anything talking to Veeam, Graph, the TSA or the Cloud is written against recorded fixtures first (`worker/tests/fixtures/<service>/`, recorded with `--record`, secrets scrubbed, served by `FakeHttpClient`). Live calls are gated behind `RP_LIVE=1` (variables in `docs/testing.md`, "Live tests"). Catch2 assertions aren't thread-safe: never use `REQUIRE`/`CHECK`/`INFO` in code a fake handler runs on the client's threads.
- Write failure-path tests before happy paths (missing item, hash mismatch, tampered signature, wrong target, unreachable service).
- Use parameterised tables (Catch2 `GENERATE`, `pytest.mark.parametrize`) for decision tables.
- Coverage floors: 80% line on `rpcore` and `cloud/app` (cloud gate is on the combined line+branch figure); 100% branch on vault, signer, target_guard, run_status (W3.3's status table), cleaner (W3.4's Cleaner, the only Worker code that deletes in the tenant), timestamper (W4.4: it decides which token is written; `src/rfc3161.cpp`, the calls into OpenSSL under it, is outside like `src/ed25519.cpp`), outbox (W4.6: `src/outbox.cpp` and `src/outbox_command.cpp` decide what is queued, sent, kept and pruned; `src/uploader.cpp`, the one HTTP call, and `src/folder_ops.cpp`, the file-system calls, are outside), service (W4.7: `src/service.cpp`, `src/service_command.cpp` and `src/service_log.cpp`; `src/scm.cpp`, the calls into the Service Control Manager, and `src/stop_signal.cpp` are outside), `app/auth`, `app/results.py`, `app/repo`. OpenCppCoverage has no branch data, so the Worker per-file floor is currently enforced as 100% line (`docs/decisions.md`). Any Worker file whose path has a part named or prefixed `vault`, `signer`, `target_guard`, `run_status`, `cleaner`, `timestamper`, `outbox` or `service` (e.g. `src/signer.cpp`, `src/signer_command.cpp`, `src/vault_dpapi.cpp`) is strict; `src/ed25519.cpp`, the calls into OpenSSL under the Signer, is deliberately outside, since the library's failure lines for a valid key can't be reached by a test (`docs/decisions.md` 2026-10-05 W4.3 point 4). Every `.cpp` under `worker/src/`, `worker/include/` and `worker/app/` must show up in the coverage report, so a file no test reaches fails; `app/` is measured through ctest's runs of `rpworker.exe`.
- A PR changing `worker/src/`, `worker/include/` or `worker/app/` without adding or changing C++ test code under `worker/tests/`, or changing `cloud/app/` without adding or changing a `.py` under `cloud/tests/`, fails CI ("No test, no merge"). Deleted tests, fixtures and `tests/e2e/` don't count.
- Every bug gets a reproducing test before its fix.
- End-to-end scenarios are tracked manually in `tests/e2e/scenarios.md`.
