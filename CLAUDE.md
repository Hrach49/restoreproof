## Project overview

RestoreProof proves that Microsoft 365 backups in Veeam Backup for Microsoft 365 actually restore.

- **Worker** (`worker/`, C++20, Windows service): samples items from a Veeam restore point, restores them through Veeam's REST API v8 into three dedicated restore targets, reads them back through Microsoft Graph, compares, cleans up, signs and RFC 3161-timestamps the result, queues it in a local outbox and uploads it to the Cloud.
- **Cloud** (`cloud/`, FastAPI, Python 3.12): dispatches jobs, verifies and stores bundles, dashboard, monthly PDF reports for MSPs. Built so far (C5.1–C5.4): the app factory, settings, JSON logging, `/healthz`, the data model and its one migration, the local Compose stack, the repository layer (`app/repo/`, the only place a statement is built or run), the tokens and `current_worker` (`app/auth/`); no API route yet. `cloud/tests` also runs the shared vectors, the schemas and `shared/tools/verify_bundle.py`.
- **Lab** (`lab/`, Python 3.12): the test tenant's canary seeder and Entra scripts. IDs in `lab/tenant.md`, the 40 canary items in `lab/seed-manifest.json`.
- **Shared** (`shared/`): the schemas, the test vectors and `verify_bundle.py`, the contract between C++ and Python.

Plan: `RestoreProof Stage 1 — Sprint Task Guide.docx`, 16 weeks, task IDs `L` lab, `W` Worker, `C` Cloud, `Q` quality, `S` sales, `P` pilots. One GitHub issue per task (#3–#95, plus #133 W4.10, #134 W4.11, #135 W4.12, #136 C5.13) on the "RestoreProof Stage 1" project; PRs say `Closes #N`. `main` is not branch-protected; the owner merges on green.

### The pipeline (`rpworker test`, as built through W4.11)

restore point → client check (the organisation `Office365`, `Worldwide`, `msid` = the profile's tenant; the manifest's tenant; the three targets resolved in that tenant) → clean before → sample (canaries + random) → target guard → restore (Veeam) → read back (Graph) → check → status → result built and validated (`restoreproof.result.v1`, invalid = `error result_invalid`) → clean after → timings → `--json <file>` (canonical bytes, never signed) **or** `--evidence <dir>` (`items.csv`, `veeam-session.log`, Ed25519 `signature.json`, RFC 3161 `timestamp.tst`, `result.json` last) → `--outbox <root>` renames the folder to `outbox\<run_id>` + `manifest.json` → `rpworker outbox flush` POSTs it to `<cloud_url>/v1/results`, 202 moves it to `sent\`.

The service (`rpworker service run`) runs that pipeline in process, one job at a time from `jobs_file`, writes `state\running.json` ahead of every step that matters, closes a run the process died in afterwards as `error interrupted|result_invalid|internal|job_invalid` (signed and queued like any run), holds while a restore of it may still run, flushes the outbox and POSTs a heartbeat to `/v1/heartbeat`.

- Defaults: `%ProgramData%\RestoreProof\` holds `vault.bin`, `runs\`, `outbox\`, `sent\`, `state\running.json`, `state\done\`, `logs\worker.log`. Named mutexes `Global\RestoreProof-restore-targets` and `Global\RestoreProof-outbox`.

## Non-negotiable rules

- **Restore targets.** Every restore goes to the `restoretest` mailbox, the `RestoreTarget` library in the RestoreTest site or alice's OneDrive `/RestoreTarget` folder (IDs in `lab/tenant.md`). Never the `RestoreTest` library or alice's `/RestoreTest` folder: those hold the canaries. `TargetGuard` runs per item inside `restore_sample` before any Veeam call, and again on the exact POST body; never trust configured IDs alone. The Cleaner is the only Worker code that deletes in the tenant: only in those three targets, each resolved through the guard's own checks first, only mails and plain files it has just listed there (`GraphClient::remove` takes a `ListedItem` only the Cleaner can make; a source scan enforces it); folders and anything else are never deleted. The app's write grants stay that narrow: `write` on the RestoreTarget list and the `/RestoreTarget` folder, `Application Mail.ReadWrite` scoped to `restoretest`; never `Sites.Selected` `write`, a `*.All` role or an Entra `Mail.ReadWrite` (`docs/security/graph-permissions.md`). Every run holds its client to the backup before anything is cleaned or restored (the client check; `error client_mismatch`); a job naming a connector this Worker lacks is `error connector_unknown` and never runs. The service's recovery adds no second deleter: its clean is the Cleaner's `before_run` clean by the record's own profile, never while a restore of ours may still run; in Veeam the hold ends only the sessions `running.json` lists as the run's own, and none of them while a restore request may have gone out and any other session of the account is running.
- **Status vocabulary.** `pass` = restore ran and 100% of items match; `fail` = an item missing or mismatched, its target read fine, Veeam not blaming infrastructure; `error` = the test itself couldn't run. Infrastructure problems are never `fail`. Veeam's own status never decides. The table is `docs/verification.md` and `rp/run_status.hpp`.
- **Secrets.** Only in the DPAPI vault (`vault.bin`; five names `veeam_username`, `veeam_password`, `graph_cert_pfx_base64`, `graph_cert_password`, `signing_key_base64`; filled by `rpworker vault set <name>` from the console or stdin, never an argument) or a gitignored `.env`. Never from an environment variable or `config.json` (which rejects secret-looking keys). Tests inject `Secrets` through each command's `load_secrets(vault)` seam. Never logged: `rp::redact()` masks the secret keys, JWTs, `Bearer` tokens and PEM private key blocks; headers and bodies are never logged. `veeam_username` is a name, not a secret value. The secret audit (`[secret_audit]`, and `fixture_secret_scan.py` with its allowlist) enforces this; `docs/testing.md` "The secret audit".
- **TLS.** Verification is never turned off. Veeam's self-signed certificate is trusted through `veeam_ca_file`, pinned through `veeam_cert_sha256` with only the host-name check skipped; a source scan fails the build on code that disables verification (reviewed exceptions all in `src/http_client.cpp`). `tsa_url` is the one URL that may be `http://`; a token is trusted for its signature, chain to `shared/tsa/tsa-ca.pem`, nonce and imprint, never for how it arrived. `cloud_ca_file` trusts a private CA for `cloud_url` (still https, host name checked).
- **Cloud tenant isolation.** All DB access through repo classes in `cloud/app/repo/` taking `msp_id: UUID` first and putting it in every `where` (`update` and `delete` too; a `get` of another MSP's row is `None`, a write of it is 0 rows); the only methods without it are `Lookup.find_worker_by_token_hash`, `Lookup.find_install_token_by_hash` (the two reads before an MSP is known) and `MspRepo.create`, held by an AST walk; `select(`, `update(`, `delete(`, `insert(` and `session.execute|get|add|scalars|…` outside `app/repo/` and `app/migrations/` (a migration runs on every MSP's rows by design) fail the lint test `tests/test_tenant_scope.py`, both walks reach a sub-package of `app/repo/`, and `tests/test_repo_isolation.py` holds every repo method on two MSPs (a new method must be added to its table; a sweep such as `RunRepo.requeue_stale` is marked `sweep=True` there, since with A's `msp_id` it may touch A's own rows and must leave B's). A connector's `config_json` is a `client-profile.v1` whose `graph_tenant_id` is its client's tenant (parsed, then compared as a uuid), and its client and Worker are read with `msp_id` by the repo itself, in the order schema, client, tenant, Worker, each refused as a `RepoError` naming the key and never a value (never left to the foreign key); every connector create, update or delete that touched a row writes one `audit_log` row in the same transaction, and one that touched none writes none; a connector's Worker and client never change. The repos flush and never commit. The database holds the same line by key (C5.2): every table but `msp` has `msp_id NOT NULL` with a key to `msp`, and every other foreign key is composite and starts with `msp_id`, so no row can point at another MSP's row; a tenant is one client per MSP (`client.tenant_id`, a `uuid`), a connector is one per Worker and client, a plan is on its own client's connector and a run under its plan's client; no foreign key cascades. A new table follows these rules, and a new migration is written by hand, names every constraint and imports nothing from `app.models`.
- **Worker tokens.** A token is 32 random bytes in base64url (43 characters); the database holds its SHA-256 alone (`worker.api_token_hash`, `install_token.token_hash`), the token is shown once and stored nowhere. `current_worker` takes it from `Authorization: Bearer <token>` (one space, nothing else), hashes, looks up, compares with `hmac.compare_digest`, and answers one 401 `{"detail": "not authenticated"}` with `WWW-Authenticate: Bearer` after the same work for a missing header, an unknown token and a revoked Worker (`revoked_at` set to anything); nothing tells a caller which. The empty token (no header, or a header of another shape) is refused after that work whatever the database holds, so a Worker row under `sha256("")` authenticates nothing. An install token expires at exactly seven days and is used once, by one `UPDATE` whose conditions are in the statement; it carries a `label`, `created_at` and `created_by` and names no client. **Registration** (C5.5, `POST /v1/workers/register`, `app/auth/registration.py`): the install token first (one 401 after the same work for an unknown, used or expired token, whatever its shape), then the key (400 for a file outside the verifiers' key-file rule, a non-canonical encoding, a `y` that is no point of the curve, or one of the fourteen small-order encodings, `app/auth/public_keys.py`; the eight points are refused because the library verifies forgeries under them, an off-curve value because nothing could ever verify under it and the operator should hear at enrolment), then `uq_worker_key_id` (409), so nothing but a 401 is answered without a valid install token; the API token is minted with `new_token()`, hashed into the row, answered once with `worker_id` and `key_id`, and the whole of it (the token's `UPDATE`, the Worker, one `audit_log` row `worker.register`) is the request's one transaction, committed before the 201 starts (`SessionDep`), so a 400 or a 409 leaves the install token unused and the Worker's first poll finds its row. The stored `public_key_pem` is the library's one three-line serialisation and `key_id` the SHA-256 of the DER, unique across all MSPs. `WorkerRepo.create` refuses `sha256("")` as a `RepoError`. Neither a token nor its hash reaches a log line (a test holds it).
- **Dispatch** (C5.6, `GET /v1/jobs`): the Worker's oldest queued runs, at most five, moved to `dispatched` with `dispatched_at` and `attempt + 1` in one statement (`RunRepo.dispatch`: a `MATERIALIZED` CTE under `FOR UPDATE SKIP LOCKED`, never `id IN (subquery)`, which Postgres rescans per outer row so the limit slides), answered as a `restoreproof.jobs.v1` document whose `run_id` is `str(test_run.id)`, `client_id` `str(client.id)`, `client` the connector's `config_json`, `connector` its type, the sizes the plan's, `restore_point` `latest`, `screenshots_enabled` the client's, no `canary_cursor`; validated against `shared/schemas/jobs.v1.json` in a test, not per request; a busy poll is three statements and an idle one two, held by a test. Every refusal a route makes is in `docs/api/openapi-v1.json` (`ErrorBody`). There is no `received` state (C5.7): the bundle's status is known in the request that receives it; `RunRepo.requeue_stale` (the sweep C5.9 calls per MSP) puts a run dispatched six hours ago or more back to `queued`, or to `expired` at three attempts, and its bundle is still taken when it comes.
- **Bundle upload** (C5.7, `POST /v1/results`, `app/results.py` and `app/routers/results.py`; `docs/verification.md` "The Cloud receives a bundle"): the Worker's parts as `outbox.cpp` sends them (`result`, `signature`, `timestamp` when there, one per listed attachment under its name), identified by name alone; the route reads the form itself under explicit limits (415 not multipart, 411 no `Content-Length`, 413 over 96 MiB before the body is read, `body: malformed`, `part_twice`; a part over its verifier limit is refused unread), since nothing else in the stack bounds a body. The Cloud **is** the Python verifier: `shared/tools/verify_bundle.py` imported by path from the image (never copied), its `verify`, `check_attachment` (public since C5.7) and `check_timestamp` in the verifiers' order under the token's Worker's `public_key_pem` and `key_id` (never anything in the body) and the one root `shared/tsa/tsa-ca.pem`; every refusal is 400 with the verifier's bare word, a part the result doesn't list is `part_unexpected`, a listed size over 25 MiB 413, a missing token `tsa_ok` null and a bad one refused (the three verifiers agree on every shared vector; two upload cases differ by design and are named in `tests/test_results_vectors.py`). The run is named only after the whole verification: one 404 `run_id: no such run` (no uuid, unknown, another MSP's, another Worker's), 409 `run_id: not dispatched` for `dispatched_at` null, `dispatched`, requeued `queued` and `expired` runs all taken (a late `error interrupted` lands), 409 `client_mismatch` (`client.client_id` = `str(client.id)`, `tenant_id` and, with `scope` `same_tenant`, `resolved.organization.tenant_id` parsed as uuids = `client.tenant_id`, no `pass`/`fail` without `same_tenant`), 409 `bundle_conflict` for a second bundle of one run, 202 with the stored state and nothing written for the same bundle again. Rows first then objects in the request's one transaction: `RunRepo.receive` (one `UPDATE`, the rowcount settles a race), `ItemRepo.create_many` (one row per `expected.items[]` joined to `check.items[]` by `index`, `position` the index, `found_sha256` always null), one `audit_log` row `result.received` `run:<id>`, then `Storage.put` under `msp/<msp_id>/runs/<run_id>/<file name>` (`bundle_key` is that prefix); 202 `{"run_id", "state"}` committed before it leaves, never a 200. A refusal after authentication writes one audit row `result.rejected` with `worker:<id> <word>` (or `run:<id> <word>` once the run is known) and is returned, not raised, so that row commits and nothing else; no refusal's text and no log line quotes the body. `app/results.py` is under `tools/check_coverage.py` at 100% line and branch.
- **Cloud settings and logs.** Nothing that is a secret or an address has a default in `app/settings.py`; the local stack's `local-only-...` values live in `docker-compose.yml` alone, and a settings fault names the variable, never a value. No log line holds a token, a password, a query string, a header or a request body; an exception is logged as its type and frames, never its message, and a library's line is its first line only; `/healthz` never returns an exception's text. Times are aware UTC (`UtcDateTime` refuses a naive one).
- **Signing contract** (C++ and Python agree, held by `shared/testdata/`): `canonical-json-v1` (`rp::canonical_json`; keys sorted by byte, `,` and `:` only, no trailing newline, refuses floats, integers outside ±(2^53−1), non-ASCII keys, invalid UTF-8; Python's `json.dumps(sort_keys=True, separators=(",", ":"), ensure_ascii=False)` gives the same bytes). `result.json` is the result's canonical bytes with nothing removed; `bundle_sha256` is its SHA-256; the signature is Ed25519 over the 32 raw digest bytes, in `signature.json` beside the result (`restoreproof.signature.v1`, five keys), never in it; `timestamp.tst` is the bare RFC 3161 token over the same digest, absent when the TSA gave none (never a status). A verifier takes the public key and the TSA CA from its caller, never the folder, and refuses a `result.json` that isn't its own canonical form (`result_not_canonical`). `rpworker signer verify` and `shared/tools/verify_bundle.py` run the same checks in the same order and print the same word; the schemas in `shared/schemas/` are the only copies (the result schema embedded into rpcore at build time, read by the Cloud by path) in the subset draft 7 and 2020-12 read alike; whoever validates in Python checks the canonical form first. The run folder's other files are covered only through the result's `attachments`; `result.json`, `signature.json`, `timestamp.tst` and `manifest.json` are never listed there.
- **API contract.** All Cloud routes under `/v1` (`/healthz` is the one probe outside it and not in the OpenAPI document; a test holds both); `docs/api/openapi-v1.json` is committed since C5.6 and held equal to what the app serves by `tests/test_openapi.py` (regenerate it with `tools/dump_openapi.py`); the CI job's own diff and the security scheme are C5.11's.
- **Report wording.** Never claim more than was tested; "fully recoverable", "guarantee", "certified", "accepted by insurers" are banned by a test.
- **Nothing is edited or re-signed.** A failed run is never edited. In a queued or sent folder only `manifest.json` is ever written after the run; the Worker deletes only `sent\` runs (over 30 days, or the oldest while `outbox\` + `sent\` exceed 500 MB), never a queued one. Under `runs\` a folder with its `result.json` is only queued; a folder without one was never signed and the service's `close_run` is its one writer, for the one folder its record names: it writes one `error` result afterwards that never says what the run found. The service lists nothing under `runs\` and adopts no folder it finds there.

## TDD workflow (enforced by CI)

- Test first: an acceptance test from the task's "Done when", then red → green → refactor per step; commit test and code together.
- Anything talking to Veeam, Graph, the TSA or the Cloud is written against recorded fixtures first (`--record`, secrets scrubbed, served by `FakeHttpClient`). Live calls are gated by `RP_LIVE=1` (`docs/testing.md`). Catch2 assertions aren't thread-safe: never in code a fake handler runs on the client's threads.
- Failure-path tests before happy paths; decision tables as Catch2 `GENERATE` / `pytest.mark.parametrize`; every bug gets a reproducing test before its fix; end-to-end scenarios tracked by hand in `tests/e2e/scenarios.md`.
- Cloud database tests run on a real PostgreSQL 16, never SQLite and never `metadata.create_all`: the schema is what `alembic upgrade head` built, each test runs in a transaction that is rolled back, a refusal is held to its constraint's name, and a database that can't be reached is a failure, not a skip.
- Exe tests check exit code, stdout and stderr exactly (no `PASS_REGULAR_EXPRESSION` or `WILL_FAIL`); none starts the service loop or names `service install|uninstall|start|stop`; no test touches `%ProgramData%`.
- Coverage: 80% line on `rpcore` and `cloud/app` (Cloud gate on line+branch combined); 100% on the strict files, held as 100% **line** in the Worker since OpenCppCoverage has no branch data. `tools/check_coverage.py` measures `app/repo` and `app/auth` since C5.3/C5.4 and `app/results.py` since C5.7 (every guarded path now exists): every branch of a repo, auth or results file needs a test (`public_keys.py` and `registration.py` are under it since C5.5). A Worker file is strict when a part of its path is, or starts with, one of `vault`, `signer`, `target_guard`, `run_status`, `cleaner`, `timestamper`, `outbox`, `service`, `client_profile`, `strict_json`, `client_check` (`worker/tools/coverage_gate.py`); strict files are decided logic over seams, no `catch (...)` of their own, and the real calls under them (`ed25519.cpp`, `rfc3161.cpp`, `uploader.cpp`, `folder_ops.cpp`, `scm.cpp`, `stop_signal.cpp`, `worker_body.cpp`, `heartbeat.cpp`, `run_folder_tail.cpp`) are outside. Cloud: 100% on `app/auth`, `app/results.py`, `app/repo`. Every `.cpp` under `worker/src`, `include` and `app` must appear in the report.
- "No test, no merge": a PR changing `worker/src|include|app` without C++ test changes under `worker/tests/`, or `cloud/app/` without a `.py` under `cloud/tests/`, fails CI.

## Coding conventions

- rpcore works in UTF-8 and reads Windows text through the wide APIs only. Messages are one line of fixed words and counts; never `what()`, a tenant value, a path or a secret in a status, a code or a log line that could leave the machine. Every logged string goes through `redact()`; `SECURITY:` lines mark a guard or owner-rule refusal.
- A new architectural choice gets a dated entry in `docs/decisions.md` (recorded before the build; "approved as written" when the owner approved it), its build notes say where the build left the entry, and the code review gets its own entry listing fixed and open findings. Update `docs/verification.md`, `docs/worker-config.md`, `docs/testing.md`, `docs/glossary.md` and this file with the task.
- Shared documents (`shared/testdata/result-v1`, `signing-v1`, `timestamp-v1`, `canonical-json-v1.json`, `client-profile-v1`, `jobs-v1`) are written by hidden `rptests "[.write_shared_*]"` cases and run by both builds; `.gitattributes` keeps `shared/schemas/*.json` and `shared/testdata/**/*.json` LF. Keys in vectors are RFC 8032's published test keys, never a secret.
- Live evidence goes under `docs/api/veeam-lab/<task>-*` with its harness; run folders, profile files and config copies stay outside the repo (`%LOCALAPPDATA%\RestoreProof\lab\`). A live harness uninstalls the service whatever happens and never replaces committed evidence with a failed run's.
