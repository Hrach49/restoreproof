## What the product does

RestoreProof proves that Microsoft 365 backups in Veeam Backup for Microsoft 365 actually restore. An on-prem **Worker** (C++, Windows service) samples items from a Veeam restore point, restores them through the Veeam REST API (v8) into dedicated test locations, reads them back through Microsoft Graph, compares them, cleans up, and uploads a signed, RFC 3161-timestamped result bundle. A **Cloud** backend (FastAPI) dispatches jobs, verifies and stores bundles, shows a dashboard, and generates monthly PDF reports for MSPs.

Worker pipeline (`rpworker test`, as built through W3.6): pick restore point → cleanup → sample select → target guard → restore → verify → status → cleanup → timings → result JSON (`--json`, unsigned); still planned: sign → timestamp → outbox → upload.

Never to the `RestoreTest` library or alice's `/RestoreTest` folder: those hold the canary files (`docs/decisions.md`, 2026-09-25). `TargetGuard` must be checked per item, inside `RestoreSample`, before any Veeam call. Any code path that could target something else is a bug. The same holds for deletes: the Cleaner (W3.4) is the only Worker code that deletes in the tenant, only in these three targets, each resolved through the guard's own checks first, and only items it has just listed there (`GraphClient::remove` takes a `ListedItem` only the Cleaner can make; a source scan enforces it). The Worker app's write grants stay that narrow: `write` on the RestoreTarget list and on alice's `/RestoreTarget` folder, `Application Mail.ReadWrite` scoped to `restoretest`; never `Sites.Selected` `write`, a `*.All` role or an Entra `Mail.ReadWrite` (`docs/security/graph-permissions.md`). Folders and anything else that isn't a plain file or a mail are never deleted.
- **Status vocabulary:** `pass` = restore ran and 100% of items match; `fail` = an item missing or mismatched, its target read fine and Veeam not blaming infrastructure for it (a failed restore counts only through its missing items; W3.3); `error` = the test itself couldn't run (Veeam unreachable, Graph auth/permission error, guard violation). Infrastructure problems must never be reported as `fail`. The decision table lives in `docs/verification.md`.
- **Secrets:** only in the Worker DPAPI vault (`%ProgramData%\RestoreProof\vault.bin`) or gitignored `.env`. Until the vault lands (W4.5), the Worker reads them from `RP_*` environment variables (names in `worker/include/rp/secrets.hpp`), never from `config.json`, which rejects secret-looking keys. Never logged; HTTP logging redacts `Authorization`, `client_secret`, `client_assertion`, `password`, `refresh_token`, `access_token`, `pfx`, `applicationCertificate` and `applicationCertificatePassword` keys, raw JWTs and `Bearer` tokens through `rp::redact()`, and never logs headers or bodies. A sentinel-grep test (W4.9) enforces this.
- **TLS:** verification is never turned off. A self-signed Veeam certificate is trusted through the `veeam_ca_file` config key, never by skipping verification. Veeam's default certificate names no host (no SAN): with `veeam_cert_sha256` also set, its public key is pinned, the chain is still verified against the CA file, and only the host-name check is skipped (`docs/decisions.md` 2026-09-26, "Veeam TLS"). A source-scan test fails the build if code that disables verification appears; its only reviewed exceptions are W1.3's best-effort revocation call, W1.5's pin statements and Q2.1's loopback-only socket callback (unit tests only), all in `src/http_client.cpp`.
- **Cloud tenant isolation:** all DB access goes through repo classes in `cloud/app/repo/` that take `msp_id` first. `select(` outside `app/repo/` fails a lint test.
- **Signing contract (shared by C++ and Python):** canonical JSON = sorted keys, no whitespace, UTF-8, ISO-8601 UTC; `bundle_sha256` is computed with `signature` and `tsa_token` removed; Ed25519 over the hash. Schema is one file, `shared/schemas/result.v1.json`, used by both builds. (`shared/schemas/` also holds `seed-manifest.v1.json`, the canary manifest's schema, and `shared/testdata/` the test vectors W3.2's C++ checker must pass: `text-v1` for mail bodies and `office-v1` for docx/xlsx content, which SharePoint rewrites; see `lab/README.md`.) `shared/tools/verify_bundle.py` is the auditor-facing verifier and must agree with the C++ `Signer`.
- **API contract:** all Cloud routes under `/v1`; `docs/api/openapi-v1.json` is committed and diffed in CI.
- **Report wording:** never claim more than was tested. Phrases like "fully recoverable", "guarantee", "certified", "accepted by insurers" are banned by a test.
- Failed runs are never edited or re-signed.

## TDD workflow (enforced by CI)

- Test first: acceptance test from "Done when", then red → green → refactor per step; commit test and code together after each green.
- Anything talking to Veeam, Graph, the TSA or the Cloud is written against recorded fixtures first (`worker/tests/fixtures/<service>/`, recorded with `--record`, secrets scrubbed, served by `FakeHttpClient`). Live calls are gated behind `RP_LIVE=1` (variables in `docs/testing.md`, "Live tests"). Catch2 assertions aren't thread-safe: never use `REQUIRE`/`CHECK`/`INFO` in code a fake handler runs on the client's threads.
- Write failure-path tests before happy paths (missing item, hash mismatch, tampered signature, wrong target, unreachable service).
- Use parameterised tables (Catch2 `GENERATE`, `pytest.mark.parametrize`) for decision tables.
- Coverage floors: 80% line on `rpcore` and `cloud/app` (cloud gate is on the combined line+branch figure); 100% branch on vault, signer, target_guard, run_status (W3.3's status table), cleaner (W3.4's Cleaner, the only Worker code that deletes in the tenant), `app/auth`, `app/results.py`, `app/repo`. OpenCppCoverage has no branch data, so the Worker per-file floor is currently enforced as 100% line (`docs/decisions.md`). Any Worker file whose path has a part named or prefixed `vault`, `signer`, `target_guard`, `run_status` or `cleaner` (e.g. `src/signer/ed25519.cpp`, `src/vault_dpapi.cpp`) is strict. Every `.cpp` under `worker/src/`, `worker/include/` and `worker/app/` must show up in the coverage report, so a file no test reaches fails; `app/` is measured through ctest's runs of `rpworker.exe`.
- A PR changing `worker/src/`, `worker/include/` or `worker/app/` without adding or changing C++ test code under `worker/tests/`, or changing `cloud/app/` without adding or changing a `.py` under `cloud/tests/`, fails CI ("No test, no merge"). Deleted tests, fixtures and `tests/e2e/` don't count.
- Every bug gets a reproducing test before its fix.
- End-to-end scenarios are tracked manually in `tests/e2e/scenarios.md`.
